# Five-minute recording runbook

## Story

> PayScope is not an unpaid-invoice emailer. It is an evidence-backed payment-operations agent that handles duplicate events, unsafe situations, uncertain provider outcomes, and delayed proof without duplicating commands or inventing recovery.

Use the deployed dashboard as the main screen. Keep the Razorpay test dashboard and a terminal available as secondary views. The terminal must show only event IDs, HTTP status, incident counts, and redacted state; never show secrets.

## What runs where

The demo kit runs locally on the operator laptop. It sends signed HTTP requests to the deployed API at `PAYSCOPE_DEMO_API_URL`. The production VPS performs enrichment, queues jobs, calls Mesh, evaluates policy, optionally creates a Razorpay Test Payment Link, sends through the configured test SMTP relay, stores receipts, and serves projections to the deployed frontend. The local kit does not start the backend and does not directly write to Razorpay.

```text
Local Node scripts -> deployed webhook endpoint -> VPS workers/Supabase -> deployed frontend
	\-> optional read-only Razorpay Test API payment lookup
```

## Before recording

1. Create a dedicated Razorpay test webhook pointing at `/webhooks/razorpay`.
2. Create a dedicated PayScope demo organization with its own policy, test SMTP recipient, and integration credentials.
3. Confirm the deployed `/health` response reports `razorpayEnvironment: "test"`.
4. Run `demo-preflight.mjs`.
5. Open the dashboard and clear any unrelated demo incidents.
6. Run `verify-demo.mjs` once to establish the baseline count.
7. Start screen recording at 1920x1080, browser zoom 90%, and hide the terminal secret values.

For a real-enrichment recording, first create a failed Razorpay Test Checkout payment and record only its payment ID. Confirm the deployed API uses the same Test account/key pair. For a real paid reconciliation, use a Payment Link generated by PayScope, complete it in Razorpay Test Checkout, and record the resulting captured payment ID and PayScope reference.

Put those values in the optional `.env` slots before starting:

```dotenv
PAYSCOPE_DEMO_FAILED_PAYMENT_ID=pay_...
PAYSCOPE_DEMO_RELATED_PAYMENT_ID=pay_...
PAYSCOPE_DEMO_CAPTURED_PAYMENT_ID=pay_...
PAYSCOPE_DEMO_PAYMENT_LINK_REFERENCE=ps_...
```

`npm run start` automatically uses filled slots as the equivalent of passing `--payment-id`. Leave a slot blank to keep that part synthetic. Never fill only one half of the captured-payment pair: the captured ID and PayScope Payment Link reference must be supplied together.

## Timeline

### 0:00-0:30 - Frame the hard problem

Open the incident feed and execution ledger. Say:

> Routine notifications are easy. The hard cases are duplicate webhooks, fraud or disputes, withdrawn consent, ambiguous provider responses, and callbacks that arrive late. PayScope is built around those failure modes.

Point out the read-only ledger, evidence timeline, policy gates, provider receipt, and reconciliation state.

### 0:30-1:10 - Signed duplicate webhook

Run:

```powershell
node docs/demo-kit/scripts/send-webhook.mjs --scenario failed-payment --event-id demo-failed-001
node docs/demo-kit/scripts/send-webhook.mjs --scenario failed-payment --event-id demo-failed-001
```

Show one incident and the duplicate response. Say:

> The payload is HMAC-verified before it is trusted. Replaying the same provider event does not create another incident or command.

Then show a related failed payment with the same order ID. Explain that correlation keeps related evidence together.

For a provider-backed version, replace the first command with:

```powershell
node docs/demo-kit/scripts/send-webhook.mjs --scenario failed-payment --event-id demo-real-failed-001 --payment-id pay_...
```

This performs a read-only Razorpay Test API lookup locally, then sends the verified provider fields to the deployed webhook. Do not use a fake `pay_demo_*` ID when claiming real enrichment.

### 1:10-1:55 - Dispute hard stop

Run:

```powershell
node docs/demo-kit/scripts/send-webhook.mjs --scenario dispute --event-id demo-dispute-001
```

Open the resulting incident and policy gates. Highlight `dispute: blocked`, no provider command, and the autonomous no-action reason.

Say:

> A technically possible email is still unsafe when an open dispute exists. The agent records the reason and refuses the external action.

### 1:55-2:35 - Consent withdrawn before dispatch

For a direct-execution deployment, use the dedicated test recipient administration workflow to suppress consent, then run:

```powershell
node docs/demo-kit/scripts/send-webhook.mjs --scenario eligible-failure --event-id demo-consent-001
```

Show that no Payment Link or SMTP receipt appears. Say:

> Eligibility is checked at execution time, not just when the plan was created. A withdrawn recipient cannot produce an external side effect.

If the deployed environment does not have direct execution enabled, show the policy gate and use the fallback narration in the final section.

Important: `eligible-failure` is still a synthetic webhook unless `--payment-id` is supplied. The recipient suppression must happen in the deployed demo organization, not in the local script.

### 2:35-3:35 - Ambiguous email boundary

Use the existing worker test or deployment fault-injection procedure to stop the worker after the durable send marker and before the SMTP result is available. Do not manufacture a fake customer email.

Show the action as `unreconciled` with `SMTP_RESULT_AMBIGUOUS_NO_RESEND`, then re-run the worker.

Say:

> The durable send marker is the ambiguity boundary. After it, retrying could duplicate customer contact, so PayScope reconciles instead of blindly resending.

### 3:35-4:25 - Verified Razorpay reconciliation

Use the test Payment Link reference produced by the direct action, then send the synthetic signed callback:

```powershell
node docs/demo-kit/scripts/send-webhook.mjs --scenario payment-link-paid --event-id demo-paid-001 --reference-id ps_<reference>
```

For real provider enrichment, include the captured test payment ID:

```powershell
node docs/demo-kit/scripts/send-webhook.mjs --scenario payment-link-paid --event-id demo-real-paid-001 --reference-id ps_<reference> --payment-id pay_...
```

The script validates that the supplied payment is actually `captured`. It does not claim that a locally generated callback was emitted by Razorpay. The real provider action is the test payment and the deployed enrichment lookup; the callback delivery remains a controlled signed demo input.

Show the causal chain in the ledger and audit view:

```text
PayScope action ID -> Payment Link reference -> receipt -> signed paid event -> confirmed outcome
```

Say:

> SMTP acceptance is not recovery. Recovery is confirmed only by a verified Razorpay event linked to the original PayScope action.

### 4:25-5:00 - Close on proof, not spectacle

Show the policy gates, audit sequence, and final incident state. Say:

> PayScope's speciality is controlled autonomy: it acts when evidence and policy allow it, refuses unsafe actions, and preserves enough provider evidence to explain the result later.

End on the execution ledger. Do not end on the illustrative landing animation.

## Fallbacks

- If a webhook is delayed, show the signed HTTP response and say the durable queue is processing; do not wait silently on camera.
- If direct execution is unavailable, show the health state and say: `The command remains queued because SMTP readiness is a safety prerequisite.`
- If a test provider callback cannot be generated, show the recorded receipt and explain that no confirmed recovery is reported without the callback.
- If the dispute event creates a separate incident, use its policy gate screen; the hard-stop behavior is the important proof.
- If the model is unavailable, show the audited unavailable/no-action outcome rather than bypassing the gate.
- If Razorpay enrichment fails for a synthetic ID, call it out as controlled degraded enrichment and show that the verified webhook still survives. Do not present that run as real provider enrichment.
- If the deployed dashboard shows only the dispute incident, remember that the synthetic dispute scenario uses a different order/customer from the failed-payment scenario. Use one real order identity when demonstrating correlation.

## Claims to avoid

Never say `email delivered` for SMTP acceptance, `payment recovered` before the signed provider event, `live payment` for synthetic data, or `Razorpay automatically handled this` as a substitute for PayScope evidence. Never call a locally generated callback a Razorpay-emitted webhook. Capture, refund, and dispute submission should be described as capability-model items unless their dedicated sandbox proof is visible in the deployed environment.
